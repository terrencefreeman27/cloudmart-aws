# Terraform Modules

Reusable, environment-agnostic building blocks — no hardcoded environment-specific values (those belong in [../environments/](../environments/)).

## `vpc/` (Phase 3) — deployed, standing
VPC, public/private subnets across 2 AZs, Internet Gateway, route tables and associations. No security groups (those live with the compute that uses them) and no NAT Gateway (deliberately deferred — see [docs/decisions/0005](../../../docs/decisions/0005-vpc-network-design.md)). Called from [`environments/dev`](../environments/dev/). See [docs/networking.md](../../../docs/networking.md) for the layout this produces.

## `compute/` (Phase 5) — designed and plan-validated, NOT deployed
An Application Load Balancer + Target Group + Launch Template + Auto Scaling Group (2 `t2.micro` instances, one per AZ), fronting the backend. The ALB and the instances both use the **public** subnets passed in as `subnet_ids` (no NAT Gateway exists, so instances need their own public IP for outbound traffic). Backend security group accepts port 4000 **only from the ALB's security group**, never a CIDR; ALB accepts HTTP on port 80 from the internet — the sole public entry point. IAM role scoped to exactly `AmazonSSMManagedInstanceCore`, no SSH, same as before. `terraform plan` confirms 14 resources, 0 to change, 0 to destroy — but this phase was **deliberately never applied**, to keep ongoing cost at $0. Full design, cost estimate, and reasoning: [docs/decisions/0007](../../../docs/decisions/0007-phase5-alb-asg-plan-not-deployed.md).

This module was rewritten for Phase 5 from its original Phase 4 form (a single directly-managed `aws_instance`, no load balancer) — that earlier design was deployed, validated, and destroyed on 2026-08-20 before this rewrite; see [docs/decisions/0006](../../../docs/decisions/0006-ec2-compute-placement-and-access.md) for that history.

## `database/` (Phase 6) — designed and plan-validated, NOT deployed
RDS for PostgreSQL (`db.t3.micro`) in the Phase 3 private subnets via a DB subnet group spanning both AZs. Not publicly accessible; database security group accepts port 5432 **only from the backend's security group**, never a CIDR, with zero egress rules (RDS needs none — the strictest security group in this project). Encrypted at rest, 7-day automated backups. Master password never handled by Terraform or this repo — `manage_master_user_password = true` lets AWS generate and own it via an auto-managed Secrets Manager secret; a scoped IAM policy (defined in `environments/dev/main.tf`, not inside either module) lets the backend's role read exactly that secret. Single-AZ by default; Multi-AZ is exposed as `var.db_multi_az` (defaults `false`) — a documented, single-flip cost upgrade, not enabled. `terraform plan` confirms 5 new resources (19 total including Phase 5's still-pending 14 — the database depends on Phase 5's backend security group by design), 0 to change, 0 to destroy — but this phase was **deliberately never applied**. Full design, cost estimate, and reasoning: [docs/decisions/0008](../../../docs/decisions/0008-phase6-rds-plan-not-deployed.md).

## `static-site/` (Phase 7) — ✅ deployed
Private S3 bucket + CloudFront distribution for the React/Vite frontend build. Bucket has all four public-access blocks enabled, is versioned and SSE-S3 encrypted, and grants read access to exactly one reader: the CloudFront service principal, via Origin Access Control, scoped by an `AWS:SourceArn` condition to this exact distribution — not "any CloudFront distribution." HTTPS via CloudFront's default certificate (no custom domain this phase). SPA routing handled via custom error responses rewriting 403/404 to `/index.html`. `PriceClass_100` (cheapest tier) by default. Independent of every other module — S3/CloudFront aren't VPC resources, so this was applied via `terraform apply -target=module.static_site` (7 resources, 0 to change, 0 to destroy) without touching `vpc`, and without deploying the still-pending `compute`/`database` modules. Frontend build uploaded and live — HTTPS, edge caching, and SPA routing all independently verified against the real deployment, not just the Terraform plan. Full design, cost estimate, and reasoning: [docs/decisions/0009](../../../docs/decisions/0009-phase7-static-site-plan-not-deployed.md).

## `monitoring/` (Phase 8) — designed, partially plan-validated, NOT deployed
CloudWatch alarms + an SNS notification topic. One alarm (CloudFront 5xx error rate) is active and genuinely deployable today at ~$0/month (`terraform plan -target=module.monitoring` confirms 2 resources — the alarm + the topic — 0 to change, 0 to destroy); eight more (ALB ×3, ASG ×1, RDS ×3) are fully written but gated behind plain `false` booleans. Deliberately **not wired to `module.compute`/`module.database`'s outputs** even while inactive — an earlier version that did reference them caused `-target=module.monitoring` to also plan creating those entire modules, a real Terraform dependency-graph hazard caught during design (see [docs/decisions/0010](../../../docs/decisions/0010-phase8-operational-polish.md)). No email is hardcoded anywhere — SNS subscription is opt-in via a gitignored `terraform.tfvars` value only. **Not applied this phase.**

This project's roadmap concludes at Phase 8 — DNS (`dns/`) and further monitoring depth were deliberately not pursued as additional phases; see [docs/ROADMAP.md](../../../docs/ROADMAP.md) "Beyond Phase 8" for the reasoning.
