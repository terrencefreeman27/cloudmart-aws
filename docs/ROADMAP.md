# CloudMart Build Roadmap

CloudMart is built in phases. Each phase adds one coherent piece of the architecture, is preceded by an explanation of the AWS services involved (what/why/alternatives/exam mapping), and — where it introduces any non-trivial AWS cost — a warning before anything gets provisioned.

Nothing here is final; phases may be re-ordered or split as the project progresses, but this is the intended path.

## Phase 0 — Project scaffolding *(current)*
Repository structure, documentation skeleton, `.gitignore`, license. No AWS resources. ✅

## Phase 1 — Local application ✅ Done
Build the minimal CloudMart app: React/Vite frontend, Node/Express backend, a couple of product endpoints and a simple cart flow, running entirely locally (no AWS). The goal is just enough app to be worth deploying — this project is not meant to become a full e-commerce platform.

## Phase 2 — AWS & Terraform foundations ✅ Done
AWS CLI and Terraform installed locally; authentication to AWS set up via **IAM Identity Center (SSO)** — short-lived temporary credentials via `aws sso login`, no long-lived IAM access keys (see [ADR 0004](decisions/0004-aws-authentication-via-iam-identity-center.md)). A minimal Terraform configuration in `infrastructure/terraform/` (provider, region/profile variables, and two read-only data sources — `aws_caller_identity` and `aws_availability_zones`) proves Terraform can reach the account, with zero `resource` blocks — so `plan` cannot create, change, or destroy anything. *SAA domains: Security, IAM, Identity Federation.*

*Deferred, not forgotten:* AWS Budgets + a billing alarm (visibility into spend before any billable resource exists) are worth setting up before Phase 4 introduces the first resource with a real per-hour cost (EC2). Not done in Phase 2 since it wasn't in this phase's agreed scope — flagged as a good candidate for the start of Phase 3 or 4.

## Phase 3 — Networking foundation ✅ Deployed
VPC across two Availability Zones, public and private subnets (one of each per AZ), Internet Gateway, one shared public route table, and one private route table per AZ — all in Terraform, via a reusable `modules/vpc` called from `environments/dev`. 13 resources, all free. Deliberately **no NAT Gateway** (it has an hourly cost, and nothing yet needs outbound internet from a private subnet) and **no security groups yet** (a security group with nothing attached to it doesn't do anything useful — those arrive in Phase 4 alongside the first EC2 instance). Full layout: [networking.md](networking.md); design reasoning: [ADR 0005](decisions/0005-vpc-network-design.md). *SAA domains: Networking, High Availability.*

## Phase 4 — Compute (single instance) ✅ Deployed, validated, torn down
One `t2.micro` EC2 instance running the backend, deployed via Terraform (`modules/compute`) into the Phase 3 public subnet. Revised mid-phase from the original "security group + key pair" plan to something stricter: **no key pair, no SSH, and no inbound security group rule by default at all** — access via AWS Systems Manager Session Manager / port forwarding only, IAM-gated rather than network-gated. Validated: instance running, registered with SSM, `GET /api/health` and `GET /api/products` both confirmed reachable through an SSM tunnel, zero ingress rules confirmed. Then **intentionally destroyed** (`terraform destroy -target=module.compute`) the same day for cost control, once validated — independently confirmed gone via `aws ec2`/`aws iam`, with the Phase 3 VPC confirmed untouched throughout. The `compute` module remains in the repo, ready to redeploy without code changes whenever a later phase needs it running again. Design reasoning: [ADR 0006](decisions/0006-ec2-compute-placement-and-access.md). *SAA domains: Compute, Security Groups, IAM (Session Manager, permission boundaries).*

## Phase 5 — Load balancing & Auto Scaling 🟡 Designed and plan-validated only, NOT deployed
Application Load Balancer + target group + Auto Scaling Group + launch template, spread across both AZs, with ELB-based health checks — this is where "high availability" becomes real. Backend security group tightened to accept port 4000 **only from the ALB's security group**, never a CIDR. Fully written in Terraform (`modules/compute`, rewritten from the Phase 4 single-instance design) and verified via `terraform plan` — 14 resources, 0 to change, 0 to destroy, zero impact on the Phase 3 VPC. **Deliberately not applied**: this phase's stated priority was $0 ongoing cost, and the ~$48.57/month this design would cost if left running (vs. Phase 4's ~13¢ for a 2-hour validation) wasn't judged worth spending just to watch it run once, since the design is fully verifiable through `plan` alone. Full architecture, cost estimate, and reasoning: [ADR 0007](decisions/0007-phase5-alb-asg-plan-not-deployed.md). *SAA domains: Elasticity, High Availability, Fault Tolerance.*

## Phase 6 — Database 🟡 PLAN-VALIDATED ONLY — NOT DEPLOYED DUE TO COST CONTROL
Amazon RDS for PostgreSQL (`db.t3.micro`) in the Phase 3 private subnets, spanning both AZs via a DB subnet group. Not publicly accessible; database security group trusts only the backend's security group, never a CIDR, and has zero egress rules (RDS needs none). Encrypted at rest, 7-day automated backups with point-in-time recovery. Master password never handled directly — `manage_master_user_password = true` lets AWS generate and own the credential via an auto-managed Secrets Manager secret, with the backend's IAM role granted narrow read access to exactly that secret. Single-AZ by default (~$15.84/mo if deployed); Multi-AZ is a documented, single-variable-flip upgrade (~$31.28/mo if deployed) — explained but not enabled. `terraform plan` confirms 19 resources total (14 still-pending from Phase 5, 5 new this phase), 0 to change, 0 to destroy, zero impact on the Phase 3 VPC — **but no `terraform apply` was run**, matching this phase's explicit $0-cost priority. Full design and reasoning: [ADR 0008](decisions/0008-phase6-rds-plan-not-deployed.md). *SAA domains: Databases, Secrets Management.*

## Phase 7 — Static assets & CDN ✅ Deployed
Private S3 bucket + CloudFront distribution (Origin Access Control, HTTPS, SPA-routing error responses) for the React/Vite frontend — **not** S3's public "static website hosting" mode, which was considered and rejected (no HTTPS, requires a public bucket, contradicts this project's private-by-default posture). Decouples static delivery entirely from the backend compute tier (Phase 4/5) — S3/CloudFront live outside the VPC altogether. Applied via `terraform apply -target=module.static_site` (7 resources, 0 to change, 0 to destroy) — deliberately targeted, not a bare `apply`, since Phases 5/6 remain intentionally undeployed. Cheapest phase by far: no idle/base charge at all (unlike EC2/ALB/RDS/NAT), effectively $0/mo at near-zero traffic. The built frontend was uploaded and independently verified: HTTPS (TLS 1.3), edge caching confirmed (`x-cache: Hit from cloudfront`), SPA deep-link routing confirmed (`200`, not 403/404), and direct S3 access confirmed blocked (`403 AccessDenied`). Full design and reasoning: [ADR 0009](decisions/0009-phase7-static-site-plan-not-deployed.md). *SAA domains: Storage, Content Delivery, Caching.*

## Phase 8 — Monitoring, security & operational polish ✅ FINAL PHASE — designed, partially plan-validated, portfolio-ready
Reprioritized from the original plan (this phase originally meant "DNS" — see "Beyond Phase 8" below for why that, and the rest of the original Phase 9-12 content, were deliberately not pursued as separate numbered phases). Covers: a CloudWatch monitoring module (`modules/monitoring`) — 1 active alarm (CloudFront 5xx error rate) + SNS topic, `plan`-validated at 2 resources / ~$0/month, **not applied**; 8 more alarms (ALB, ASG, RDS) fully designed but inert until Phase 5/6 deploy; a full logging design (application, ALB, RDS, CloudFront — destinations, retention, cost) documented but nothing enabled, since three of the four have nothing to log yet; a security synthesis pulling together every prior phase's IAM/network/secrets/encryption decisions into one production-hardening checklist; a reliability synthesis (health checks, ASG replacement behavior, Multi-AZ, backups, RTO/RPO by failure scenario); a cost-controls summary distinguishing fixed-charge vs. usage-based vs. deployed vs. intentionally-undeployed resources; and a new operational runbook ([docs/runbook.md](runbook.md)). A real Terraform dependency-graph bug was found and fixed while building the monitoring module — see [ADR 0010](decisions/0010-phase8-operational-polish.md) for the general lesson, not just the fix. *SAA domains: Monitoring, Operational Excellence, Security, Reliability.*

## Beyond Phase 8 — deliberately not pursued as further numbered phases
The original plan continued through Phase 12 (DNS, deeper security hardening, dashboards, remote Terraform state, final docs polish). Phase 8 is where this project's active build stops — everything below is documented here as honest "what I'd do next" scope, not as pending work:

- **DNS / custom domain** (Route 53 hosted zone + ACM certificate on both CloudFront and the ALB) — has a small fixed monthly cost ($0.50/mo per hosted zone) that was never explicitly approved, and isn't necessary to demonstrate the underlying architecture.
- **Deeper security tooling** — AWS WAF, Config, Security Hub, GuardDuty, VPC Flow Logs, CloudTrail with a dedicated log-archive account. All have real cost and are genuinely valuable in production; see the production-hardening checklist in [docs/security.md](security.md).
- **CI/CD pipeline** — automated `plan`-on-PR / `apply`-on-merge, automated frontend build/deploy/invalidate. Currently manual (see [docs/runbook.md](runbook.md)).
- **Remote Terraform state** (S3 backend + DynamoDB locking) — meaningful once there's more than one operator; not yet needed for a single-person project.
- **Containers (ECS/EKS), multi-region, serverless (Lambda) rewrite** — legitimate architectural alternatives worth discussing in an interview ("how would you scale this further"), out of scope for what this project set out to demonstrate.

These are natural "v2" talking points, not gaps in what was built.
