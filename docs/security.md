# Security Considerations

This document tracks the security posture of CloudMart as it's built, and the reasoning behind it. It gets filled in incrementally — each section is populated when the corresponding phase (see [ROADMAP.md](ROADMAP.md)) is implemented.

## Identity & access management
*(Phase 2, 9)*
- No use of the AWS root account for day-to-day work.
- **CLI/Terraform authentication uses AWS IAM Identity Center (SSO), not long-lived IAM access keys.** Running `aws sso login --profile cloudmart` opens a browser-based login and exchanges it for short-lived, auto-expiring temporary credentials (cached locally, never committed anywhere). Terraform's AWS provider references the `cloudmart` profile by name only — see [providers.tf](../infrastructure/terraform/providers.tf) — and has no awareness of how that profile authenticates. This eliminates the entire risk class of a long-lived secret key sitting in a config file waiting to be leaked. See [ADR 0004](decisions/0004-aws-authentication-via-iam-identity-center.md).
- The `cloudmart` profile assumes an IAM Identity Center permission set (`PowerUserAccess`) — broad, but time-boxed to the session rather than permanent, and revocable centrally from Identity Center without rotating any key.
- **PowerUserAccess deliberately excludes IAM management** — confirmed the hard way in Phase 4, when creating the backend's EC2 instance role failed with `AccessDenied` on `iam:CreateRole`. This is an intentional AWS guardrail: it stops a "power user" from self-escalating to admin by creating a new role with `AdministratorAccess` and attaching it to something they control. Resolved by attaching a narrowly-scoped custom policy to the permission set — role/instance-profile management limited to `cloudmart-*`-named resources, `AttachRolePolicy` limited by condition to only the `AmazonSSMManagedInstanceCore` ARN, `PassRole` limited by condition to `iam:PassedToService = ec2.amazonaws.com` — rather than widening the whole permission set to something broader. Full writeup: [ADR 0006](decisions/0006-ec2-compute-placement-and-access.md).
- EC2 instances use IAM instance roles for AWS API access — never long-lived access keys baked into the instance. The backend's role (Phase 4, and carried forward unchanged into the Phase 5 design) is scoped to exactly `AmazonSSMManagedInstanceCore`, nothing else.
- Principle of least privilege applied to every policy, documented per-resource as it's created.

## Network isolation
*(Phase 3, 4, 6)*
- The data tier (RDS) lives in private subnets. The backend compute tier does **not**: both the Phase 4 instance and the Phase 5 ASG design use the public subnets, because the VPC has no NAT Gateway (a deliberate cost decision) and the instances need outbound internet. Their protection comes from security groups instead — no inbound rule except the app port from the ALB's security group. Moving them to private subnets behind a NAT Gateway or VPC endpoints is listed in the production hardening checklist below.
- Security groups are scoped by reference to other security groups (e.g. "allow from the ALB's security group") rather than broad CIDR ranges wherever possible.
- **Phase 4's backend EC2 instance had zero inbound security group rules by default** — it sat in a public subnet (a deliberate, documented Phase 4 trade-off, see [ADR 0006](decisions/0006-ec2-compute-placement-and-access.md)), but nothing was open to the internet on any port, including SSH. Access was exclusively via AWS Systems Manager (Session Manager shell, or port forwarding for the app itself), which is IAM-gated rather than network-gated.
- **Phase 5's design realizes the "ALB as sole public entry point" goal** (designed, plan-validated, **not deployed** — see [ADR 0007](decisions/0007-phase5-alb-asg-plan-not-deployed.md)): the backend security group's only ingress rule references the ALB's security group ID, never a CIDR — port 4000 has no path from the internet under any circumstance, direct or otherwise. The ALB's security group is the only one with a CIDR-based public rule (`0.0.0.0/0` on port 80), and its own egress is restricted to the backend security group on port 4000 rather than egress-all. Instances still sit in public subnets (still no NAT Gateway budgeted), but are unreachable from anywhere except the ALB regardless of subnet type.
- **Phase 6's database design goes one step further** (designed, plan-validated, **not deployed** — see [ADR 0008](decisions/0008-phase6-rds-plan-not-deployed.md)): the database's security group ingress references the backend's security group ID, never a CIDR, and the database sits in the Phase 3 **private** subnets — no path from the internet, and no path from anything in the VPC except the backend tier specifically. `publicly_accessible = false` is set explicitly, not left to a default. Unlike every other security group in this project, the database's has **zero egress rules at all** — it doesn't need to initiate outbound connections, so nothing was granted, not even the usual "outbound for updates" allowance the backend needs.

## Secrets management
*(Phase 6)*
- Database credentials and any other secrets live in AWS Secrets Manager, not in environment files, Terraform variables committed to Git, or application code.
- `.gitignore` blocks `.env*`, `*.tfvars`, and common credential file patterns — see the repo root [.gitignore](../.gitignore).
- **The Phase 6 design (plan-validated, not deployed) goes further than "store the secret somewhere safe": it never generates the secret itself in a place we could leak it.** `manage_master_user_password = true` on the RDS instance means AWS generates the master password internally and stores it in a Secrets Manager secret it creates and owns — the password never appears in Terraform code, Terraform state, this repo, or this conversation. The backend's IAM role is granted a narrowly-scoped policy (`secretsmanager:GetSecretValue` on exactly that one secret's ARN, nothing broader) to read it at runtime, continuing the least-privilege pattern from [ADR 0006](decisions/0006-ec2-compute-placement-and-access.md).

## Data protection
*(Phase 6, 7)*
- **RDS storage encryption at rest** (Phase 6 design, plan-validated, not deployed): `storage_encrypted = true`, set at creation — this AWS provider argument cannot be changed on an existing instance without a snapshot-and-restore, so the design gets this right from the start rather than as a later fix.
- **The Phase 7 frontend S3 bucket is fully private, not merely "not publicly writable"** (deployed 2026-08-20 — see [ADR 0009](decisions/0009-phase7-static-site-plan-not-deployed.md)): all four S3 public-access block settings are enabled (`block_public_acls`, `block_public_policy`, `ignore_public_acls`, `restrict_public_buckets`), and the only reader permitted at all is CloudFront, via Origin Access Control — the bucket policy grants `s3:GetObject` to the CloudFront service principal specifically, scoped further by an `AWS:SourceArn` condition to this exact distribution's ARN, not "any CloudFront distribution." Encrypted at rest (SSE-S3) and versioned, protecting against accidental overwrite or deletion of a deployed build. **Independently verified post-deployment, not just inferred from code:** `aws s3api get-public-access-block` confirms all four blocks `true`; direct requests to both the bucket's regional REST endpoint and its path-style URL both return `403 AccessDenied`; the site is only reachable through the CloudFront domain, over HTTPS (TLS 1.3 confirmed).

## Monitoring & logging
*(Phase 8)*
- A CloudWatch alarm (CloudFront 5xx error rate) + SNS topic is designed and `plan`-validated (`modules/monitoring`), genuinely deployable at ~$0/month (CloudWatch's always-free tier covers 10 alarm-metrics/month; this is 1). **Not applied this phase** — left for separate approval, same discipline as every other resource in this project regardless of estimated cost. See [ADR 0010](decisions/0010-phase8-operational-polish.md).
- Eight more alarms (ALB ×3, ASG ×1, RDS ×3) are fully written but gated behind plain `false` booleans, deliberately **not referencing `module.compute`/`module.database`'s outputs at all** — an earlier design that did reference them caused `-target=module.monitoring` to silently plan creating those entire modules as a side effect (a real Terraform dependency-graph hazard, not a CloudMart-specific bug — see the ADR for the general lesson). Enabling real compute/database monitoring is a deliberate two-line edit when those phases actually deploy, never an accidental side effect of planning something else.
- No logs are currently shipped anywhere (application, ALB access, RDS, or CloudFront) — there's nothing to log yet for three of those four (Phase 4/5's app, ALB, and Phase 6's RDS are all undeployed), and CloudFront logging was deliberately not enabled for near-zero traffic with no active debugging need. Full logging design (destinations, retention, cost) is documented, not deployed — see [docs/cost.md](cost.md) and [docs/architecture.md](architecture.md).
- **Retention is a security control, not just a cost one:** CloudWatch Logs' default retention is "Never expire," which silently accrues both storage cost and an ever-growing, unmanaged audit trail. Every future log group in this project is designed to set explicit retention (14-30 days for a portfolio project) rather than accept that default.

## Production hardening checklist
What a real production deployment of this architecture would add, beyond what CloudMart currently builds or designs — useful as an explicit "here's what I'd do differently with a production SLA and budget" answer:

| Area | CloudMart (this project) | Real production |
|---|---|---|
| IAM | `PowerUserAccess` for the human operator (Terraform), scoped custom policies for service roles | Least-privilege custom policies for humans too, no broad AWS-managed policies, permission boundaries, SCPs if multi-account |
| HTTPS | CloudFront's free default certificate, no custom domain | ACM certificate + custom domain on both CloudFront and the ALB (the ALB currently only supports plain HTTP — see [ADR 0007](decisions/0007-phase5-alb-asg-plan-not-deployed.md)) |
| Database availability | Single-AZ by default, Multi-AZ as an opt-in variable | Multi-AZ on by default for anything holding real customer data |
| Deletion protection | Off everywhere (`deletion_protection = false`, `skip_final_snapshot = true`) — intentional, so this project can be destroyed/redeployed freely | On for RDS and the ALB; final snapshots required before any RDS deletion |
| Secrets rotation | Static (AWS-generated once, via `manage_master_user_password`) | Automatic rotation via Secrets Manager's rotation Lambda, on a schedule |
| Backend placement | EC2 instances in public subnets with a public IP (no NAT Gateway); inbound locked to the ALB's security group only | EC2 in private subnets, outbound via per-AZ NAT Gateways (or VPC endpoints for SSM/S3/Secrets Manager with a pre-baked AMI), no public IPs on instances |
| Network protection | Security groups only | + AWS WAF in front of CloudFront/ALB, + AWS Shield for DDoS, + VPC Flow Logs |
| Compliance/audit tooling | None (out of budget scope) | AWS Config, Security Hub, GuardDuty, CloudTrail with a dedicated log-archive account |
| Terraform state | Local, single operator | Remote (S3 + DynamoDB locking, or Terraform Cloud), multiple operators, CI/CD-driven applies |
| Alerting | SNS email (optional, not deployed) | PagerDuty/Opsgenie integration, on-call rotations, runbook-linked alarms |
| Deployment | Manual `terraform apply` + manual `aws s3 sync` | CI/CD pipeline (GitHub Actions or similar) with automated plan-on-PR, apply-on-merge, and automated frontend build/deploy/invalidate |

## Future considerations (not in current scope)
- AWS WAF in front of CloudFront/ALB — has a cost, evaluated here but deferred (see table above).
- AWS Config / Security Hub for continuous compliance monitoring — good talking point for interviews, out of scope for this project's budget.
